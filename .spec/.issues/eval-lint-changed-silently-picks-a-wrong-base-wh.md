Worth recording alongside it: the criterion for telling the two branch classes apart, since the obvious tests are wrong.   - 'is the trunk an ancestor of HEAD' does NOT discriminate. It answers NO for any ordinary branch that is merely behind the trunk.   - 'is the branch point an ancestor of the trunk' is VACUOUS — a merge-base is by definition a common ancestor, so it answers YES for both classes, including a provably contaminated branch (measured: branch point ~6 weeks stale, still YES).   - What does discriminate is MAGNITUDE: orphaned pre-rewrite history diverges by thousands of commits in BOTH directions (measured 5720 / 5763), while behind-the-trunk is a small one-way gap (measured 3 / 8, and 5 / 0 on another).   - For the separate question of whether such a branch may be PUSHED, the tree is not enough: a tree-level grep for a purged string can be washed clean by one more commit while the old blobs still ride the tip (measured: 5 files in the tree, 6 commits touching it in history). Pushability must be measured over history with a pickaxe scoped to trunk..HEAD, which has the bonus of self-excluding whatever the trunk itself already carries.   So: commit magnitude as the screen, tree grep for 'does the current content still carry it', history pickaxe as the decision on pushability. Merging the current trunk into a pre-rewrite branch fixes the MEASUREMENT BASE but not the contamination; such a branch must be redone onto the new trunk, not pushed.

Worth recording alongside it: the criterion for telling the two branch classes apart, since the obvious tests are wrong.
  - 'is the trunk an ancestor of HEAD' does NOT discriminate. It answers NO for any ordinary branch that is merely behind the trunk.
  - 'is the branch point an ancestor of the trunk' is VACUOUS — a merge-base is by definition a common ancestor, so it answers YES for both classes, including a provably contaminated branch (measured: branch point ~6 weeks stale, still YES).
  - What does discriminate is MAGNITUDE: orphaned pre-rewrite history diverges by thousands of commits in BOTH directions (measured 5720 / 5763), while behind-the-trunk is a small one-way gap (measured 3 / 8, and 5 / 0 on another).
  - For the separate question of whether such a branch may be PUSHED, the tree is not enough: a tree-level grep for a purged string can be washed clean by one more commit while the old blobs still ride the tip (measured: 5 files in the tree, 6 commits touching it in history). Pushability must be measured over history with a pickaxe scoped to trunk..HEAD, which has the bonus of self-excluding whatever the trunk itself already carries.
  So: commit magnitude as the screen, tree grep for 'does the current content still carry it', history pickaxe as the decision on pushability. Merging the current trunk into a pre-rewrite branch fixes the MEASUREMENT BASE but not the contamination; such a branch must be redone onto the new trunk, not pushed.)
