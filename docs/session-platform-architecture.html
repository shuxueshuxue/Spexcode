Session Platform 总体设计

一个与 SpexCode 解耦、以 SQLite 为持久状态、以固定通信协议为底座、由 topology 与 adopter runtime 逐层组合的 session 平台。

核心决定：发布完整名称的 session-communication-protocol，不使用容易与 Secure Copy Protocol 混淆的 SCP；TypeScript 是第一实现，SQL schema 与 conformance suite 才是跨语言契约。
本页目录 目标与非目标 总体分层 固定协议 Topology Runtime 与配置 三个 adopter 数据库与路径 TypeScript / Rust 保留与删除 Package 与仓库 验收标准

1. 目标与非目标

这个系统只解决一类问题：在同一台机器上，让不同进程用一套固定语言建立 session 地址、排队消息、读取消息，并允许上层组合关系、运行时控制和 harness 配置。

Self-launch 是主路径

没有 dashboard、没有 backend、用户直接启动 Claude/Codex 时，协议地址、离线排队和显式监听仍然成立。

协议不认识产品

它不知道 Spec、Git、parent、lifecycle、tmux、native thread、input box 或 dashboard。

一个机制覆盖三种采用方式

ZSwarm、self-launch、Spex governed 使用相同 enqueue/dequeue 和数据库约束，不存在 protocol mode。

物理位置由 adopter 决定

协议只接收显式绝对 database path，不要求 ~/.spexcode、项目 cwd 或固定文件名。

明确非目标

  • 不做分布式消息代理，不支持多台机器直接共享同一个 SQLite 文件。
  • 不在协议中管理 harness launch、liveness、stop、resume 或模型回复。
  • 不承诺 dequeue 之后的外部 input 操作成功；dequeue 本身就是协议交付。
  • 不发布一个包含所有 adopter 分支的通用 runtime daemon。

3. 固定的 Session Communication Protocol

协议是一个封闭系统。无论外部 adapter 是 Codex、Claude、OpenCode、Pi、ZSwarm 还是未来实现，内部语言保持不变。

操作固定语义不包含
initialize(sessionId)建立精确、不可误拼创建的协议地址不创建 worktree，不启动 harness
enqueue(target, message)原子写入不可变消息并加入 FIFO；支持 idempotency key不查 parent，不尝试 input
dequeue(target)原子移除并返回 FIFO head；返回即视为协议交付没有 claim、ack、settle 或 adapter callback
listPending(target)无副作用读取当前有序待处理消息不持久化 reader cursor
readMessages(target, after?)按稳定 sequence 读取历史不解释 message kind
retire(sessionId)禁止新 enqueue，保留可审计 tombstone；清理由 adopter 决定不关闭进程，不删 worktree

公开名词只保留 session、message、queue、producer、consumer、enqueue 和 dequeue。不公开 take、accept、owed、settled 或 delivered 等重叠状态。

边界选择：进程若在 dequeue commit 后、adapter 接收前崩溃，消息不会自动回队。这是已经选择的 at-most-once ownership transfer。需要更强保证的 runtime 自己维护 consumer inbox，以 messageId 幂等处理；不能扩展核心队列状态机。

4. Topology 只管理关系

父子、watch、subscription 是图关系，不是消息属性，也不是 harness 能力。Topology 只回答“谁与谁有什么关系”，由 adopter policy 决定“这次变化应通知谁、通知什么”。

Topology operations
  attach(parent, child, relationType)
  detach(edgeId)
  reparent(child, nextParent)
  subscribe(watcher, subject, channel)
  parents(sessionId)
  children(sessionId)
  subscriptions(sessionId)

在单个 SQLite 数据库内，关系变更与对应 message enqueue 可以放进同一个 ACID transaction，因此 v1 不需要 transactional outbox。只有未来跨数据库、外部 broker 或网络服务时，outbox 才重新获得独立价值。

禁止双重真相：session.parent 与 watchers.json 不能同时作为权威。最终只有规范化 edge table 是关系事实；parent/children/watchers 都是查询投影。

5. Runtime adapter 与 configuration adapter 分开

模块负责不负责
Harness runtime adapterlaunch、native input、interrupt、stop、liveness、native identity、cold proof不生成 hooks，不定义 queue 状态
session_runtime_bindingsprotocol address → native runtime identity、start token、generation fence不拥有 protocol session、topology、liveness 或 dequeue ack
Harness configuration adaptermaterialize contract、hooks、commands、skills、trust/config 文件不持有进程，不 dequeue
Adopter runtime何时轮询/唤醒、dequeue 循环、输入组合、错误策略不修改协议语义

当前巨大的 harness interface 应拆成这两个 facet。一个 registry row 可以同时提供两个 facet，但 self-launch 只需要 configuration facet 和一个显式 listener，不应被迫拥有 managed runtime。

Logical session 与 native runtime 的绑定

session_runtime_bindings 是 adopter-owned component，而不是 protocol 的扩展列。它以 (namespace, protocol_session_id) 为键，保存 native identity、start token 和 generation fence。 runtime 在 dequeue 前解析并验证 binding；重启时同一个 protocol address 可以绑定新的 native runtime，旧 generation 不能覆盖新绑定。unbind 不 retire address，也不触碰 pending queue。

跨进程通信的核心不是 observer：producer 进程直接 import protocol package 并 commit SQLite；runtime 进程通过查询同一数据库发现消息。Shell hook 不能 import 时调用一个极薄 CLI，该 CLI 仍只是同一 library 的入口，不是 daemon。

7. 数据库作用域与路径

协议不规定数据库文件名。Host 传入显式绝对 databasePath，因此不会出现 spexcode.db 或 session-protocol.sqlite 被误当成跨产品标准的情况。

Standalone session manager  -> <stateRoot>/sessions.db
SpexCode adopter            -> <spexStateRoot>/spexcode.db
ZSwarm adopter             -> <zswarmStateRoot>/zswarm.db

openSessionDatabase({ databasePath: absolutePath })

默认作用域是一个 application state instance 一个数据库。SpexCode 的同一 state root 下，所有 backend 共享一个数据库，用 project_id 区分项目；不是每个 session 一个数据库，也不是强迫整台机器上的所有应用共享一个数据库。

只有一个必需的 durable root

  • Config file 只是定位 state root 的 bootstrap 文件，不是另一份状态根。
  • State root 保存数据库和 artifacts，是唯一必需的持久根。
  • Runtime directory 只在 socket 路径、PID 文件等临时资源确有需要时存在，可使用 OS runtime dir；它不是持久事实。
  • Materialized harness files 位于 harness 规定的项目路径，因为它们必须被发现，不属于全局数据库。

解析优先级固定为：显式 API/CLI 参数 → 环境变量 → adopter 全局 config → OS 标准默认。Config 文件自身的位置也可通过显式参数或环境变量重定位，避免固定依赖 ~/.spexcode。

解析出路径还不够，还要判定 locality，且默认拒绝。 绝对 databasePath 解析完成之后、调用 openSessionDatabase 之前，adopter path resolver 必须确认该路径位于 本地且支持可靠 advisory locking 的 filesystem；非本地、或 locality 无法判定，一律 fail closed（allow-list 而非 deny-list）。 协议核心不做、也不假装做这个判定，它只接收已判定合格的绝对路径。原因：v1 用 DELETE 而非 WAL，而 WAL 因要求共享内存会在网络 filesystem 上自动 fail loud、DELETE 不会——那道白送的闸门没有了，必须显式补上。macOS/Windows detector 仍是实现 OPEN， 缺失时同样拒绝；真实网络挂载未实测，不宣称覆盖。

地址空间在一个 databasePath 内是扁平且全局的：session_id 全局唯一、单列主键，协议不接受 (project_id, session_id)。project_id 只是 adopter metadata（存在 spex_governed_sessions 这类 adopter 表里）， 多项目共库时由 adopter 自己保证 id 全库唯一；人类可读的短 id 是 adopter 维护的 project-local alias，传给协议的仍是全局 id。

8. TypeScript first，Rust ready

第一实现使用 TypeScript，编译为 JavaScript；SQLite C engine 负责真正的数据结构、锁和恢复。SQL schema、migration 和 conformance fixtures 是语言无关契约。

选择现在的判断触发改变的事实
TypeScript采用当前三个 adopter 都从 Node/SpexCode 生态进入；可直接 import；不增加 daemon 或 N-API 发布面。代价（须一并记账）：node:sqlite 把 SQLite 版本与 Node 构建绑死，无法独立钉版
Driver：node:sqlite DatabaseSyncv1 冻结零安装、无 native ABI、外部 adopter 接入税最低。better-sqlite3 作为可替换实现被验证过（同一套 vector 45/45 通过），但 27MB 与 native prebuild 是真实接入成本
Rust保留第二实现位置真实非 Node adopter、需要独立跨语言 runtime、必须捆绑同一 SQLite、或测得 JS boundary 是瓶颈
ORM不采用表少且 SQL 是协议资产；ORM 会建立第二套 schema 语言

Runtime 必须在启动与 CI 查询 sqlite_version()，并且是数值比较而不是字符串比较（"3.9.0" 字符串大于 "3.38.0"，却老十六年）。

最低版本 = SQLite 3.38.0，由引擎实际用到的 SQL 特性推导，不是从某个 bug 反推。 逐条出处：partial index 3.8.0 · STRICT tables 3.37.0 · JSON 函数成为内置 3.38.0（changelog 原文：“The JSON functions are now built-ins. It is no longer necessary to use the -DSQLITE_ENABLE_JSON1 compile-time option”）。卡点是 JSON 这条而不是 STRICT——在 3.38.0 之前使用 json_valid 等于依赖对方编译时开没开 SQLITE_ENABLE_JSON1，而依赖编译开关不构成版本下限。 该下限有专门 vector 逐特性验证。

Fleet 结论（实测）：Node 22.21.0 自带 SQLite 3.50.4，高于 3.38.0，整套引擎与并发/crash vector 在其上 55/55 通过。因此 engines: node >= 22 与 .nvmrc 维持不变。（参考：Node 24.14.0 = 3.51.2，24.15.0 = 3.51.3。）

WAL 不在 v1 内。SQLite 的 WAL-reset bug 存在于 3.7.0 至 3.51.2、修复于 3.51.3，而其触发条件正是本架构的形态： WAL 模式下两个以上连接同时写或 checkpoint。v1 因此固定使用 rollback journal DELETE 并禁用 WAL——绕开该 bug，同时保住 Node 22。 启用 WAL 是未来一次独立升级实验，前置条件是 SQLite >= 3.51.3，不属于 v1 合同。

9. 扩展后做减法

元素决定理由
SQLite database + rollback journal保留唯一结构化持久状态与跨进程 transaction authority。v1 是 DELETE 模式，写事务期间出现 -journal、提交后消失；不产生 -wal/-shm
Protocol session/message tables保留地址、FIFO、历史、幂等与 retire 的最小事实
Topology edge tables内部保留消除 parent/watcher 双重真相
每 session 的 pending/timeline/journal/cursor JSON删除数据库 transaction 与查询已提供同一能力
应用 lock files删除SQLite 锁负责数据库状态；runtime process proof 仍由 adapter 自己拥有
Protocol outbox删除同库 topology mutation + enqueue 可在一个 transaction 中完成
Filesystem observer 作为正确性来源删除事件不可保证；wake 只能降低延迟，查询数据库才是事实
通用 SessionRuntime class/package暂不创建三个 adopter 的 loop 不同，共享类只会装 policy switch
Consumer inbox按需 adopter-owned只有要求 dequeue 后可重试的 runtime 才需要
Artifacts 与 materialized files数据库外保留大文件与 harness-discovered files 不适合变成数据库 blob

10. Package 与仓库策略

@session-platform/session-communication-protocol   published
  - database open/config validation
  - protocol schema + migrations
  - enqueue/dequeue/read/retire
  - conformance fixtures

session-topology                                  internal first
  - own migrations and edge queries
  - publish only after two adopters prove identical semantics

adopter runtime modules                          adopter-owned
harness runtime/configuration adapters            adopter-owned

Package 名使用全名，不缩写为 scp。新 repository 可以是最终归宿，但不应在 schema、migration 和两个真实 adopter 尚未稳定时先拆仓库。先在现有 monorepo 以独立 package 和 conformance suite 落地；当 Spex governed 与另一个 adopter 都通过后，再抽取 repository，避免把尚在变化的内部耦合固化成跨仓边界。

11. 架构验收标准

  1. Self-launch 在没有 backend 时可 initialize、被 enqueue，并在之后显式 listen/dequeue。
  2. Spex governed 的 CLI、hook 和 dashboard producer 共享同一 protocol implementation。
  3. ZSwarm adopter 不 import Spex lifecycle、Git layout 或 harness adapter。
  4. 任何 topology mutation 与必要 notification enqueue 在一个 SQLite transaction 内完成，无 outbox。
  5. 丢失、重复或延迟 wake 不改变正确性；runtime 重启后仅查询数据库即可恢复。
  6. 协议 package 不读取 cwd、.spexcode 或 product config，只接收显式 database path。
  7. 所有写 transaction 都是同步短事务，内部不执行网络、文件、harness 或用户 callback。
  8. 多进程、SIGKILL、busy、checkpoint starvation、migration replay 与 backup restore 测试通过。
  9. 启动时 sqlite_version() 低于 3.38.0 一律拒绝；journal_mode 回读必须是 delete，绝不自动转换一个 WAL 库。
  10. storage locality 由 adopter path resolver 在 openSessionDatabase 之前判定并 fail closed；非本地或无法判定即拒绝。协议核心不做也不假装做该判定。
  11. 一个进程内不得链接两份 SQLite build 打开同一个库：POSIX advisory lock 是 per-process 的，两份 build 互相看不见，single-writer 会静默失效（实测：持锁方仍在持锁时，另一份 build 0ms 就拿到了写锁）。
  12. dequeue 是 at-most-once 协议交付边界；consumer handler journal 属 adopter，且不与 dequeue 同事务，任何实现都不得宣称协议级 at-least-once。
