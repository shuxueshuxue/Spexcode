数据库基础与 Outbox

先建立数据库的基本模型，再观察“状态变更”和“发送消息”为什么需要一个事务发件箱。所有演示都在浏览器内运行，不依赖服务端。

先把数据库想成四层

数据库不是“一个神秘文件”，而是对持久化状态、并发和恢复做出明确承诺的一组机制。

表 Table

同一种对象的集合，例如 messages 表。

行 Row

表中的一条记录，例如一个 message。

列 Column

记录的字段，例如 session_id、body。

事务 Transaction

一组操作作为一个整体提交或回滚。

提交 Commit

数据库对外宣布：这次事务已经成为事实。

索引 Index

为查询建立的辅助结构，换空间买读取速度。

关键直觉程序崩溃只能发生在“事务提交前”或“事务提交后”。数据库要保证不会出现半个事务。

WAL、锁和并发

概念它解决什么它不承诺什么
WAL先记录变更，再把变更合并到主数据库；读者可以继续读取旧快照。不让多个写事务同时提交。写事务仍需排队。
写锁确保两个 writer 不会同时破坏同一份状态。不保证永不等待。磁盘暂停或长事务仍会造成延迟。
busy timeout让短暂的写冲突等待一小段时间。不应该掩盖长期持锁；超时必须报错。
索引让按 session_id 查 pending 变快。不改变事务的正确性，也不是消息历史本身。

我们的原则：事务内不调用 harness、网络、Git、模型或用户 callback。数据库只做短暂的本地状态变更。

它解决什么问题？

状态提交成功后，发送方进程可能马上崩溃。outbox 保留“还要发什么”的事实，dispatcher 重启后可以继续。

  • 状态和发送意图在同一事务提交。
  • 发送成功但标记失败时，用 idempotency key 重试。
  • 接收方不需要知道发送方是否崩溃。

它不是什么？

outbox 不是第二个 inbox，也不是 queue 的确认状态。

  • outbox：发送方待发送意图。
  • queue：接收方 pending 消息。
  • WAL：数据库内部的恢复机制。
  • adapter：dequeue 后才调用 harness。

术语表

这些词在整个 session communication architecture 中保持固定含义。

Transaction

一组数据库操作的原子单位，要么全部提交，要么全部回滚。

Commit

事务成为可见事实的线性化点。

Rollback

事务没有提交时，撤销本次事务的所有修改。

WAL

Write-Ahead Logging。数据库先记录变更，再更新主数据。

Writer

请求修改数据库的进程或连接；多个 writer 仍会争用一个写提交序列。

Reader

读取数据库快照的进程或连接；WAL 允许读写并行。

Outbox

发送方事务中的待发送意图，属于 adopter，不属于通用 queue。

Idempotency

同一个操作重复执行，结果仍等价；重试不会产生重复消息。

Dequeue

从接收方 FIFO queue 原子移除一条消息；协议层在此完成 delivery。

Index

服务查询的辅助结构，例如按 target session 查 pending。
