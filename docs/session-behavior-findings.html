Session Behavior Findings

A product-level behavior study of weakly instructed ZCode sessions. The question is whether task work, tool turns, durable session state, isolated workspaces, and clean evaluation agree about what actually happened.

Product under test: z-code proposal d97c3e87e | real compiled CLI | bigmodel/glm-5.3 | ZCODE_FEATURE_SWARM=1 | measurement head 6c45eb4ee

Executive Summary

Primary correctness finding: an incomplete provider or tool turn must never become process exit 0 plus a successful idle session projection.

Across the studies, the most important failures were not lost SQLite messages or phantom parent-child edges. They were false completion signals: the system can have no assistant completion, no tool result, and no delivered workspace change while the outer process is still treated as successful or remains indefinitely unresolved.

Two independent delivery problems also appeared: code that works only because a dependency exists on the host, and agents that write outside the requested repository. Those belong at the adopter and launcher boundaries, not in session-core fallbacks.

Method

  • Official iterative benchmark tasks, with only the current checkpoint text supplied to the model.
  • Short instructions; no forced decomposition, no forced Swarm children, no hidden tests, no reference solutions, and no evaluator feedback fed back into later turns.
  • Each problem used its own random root, Git repository, storage directory, session, temporary directory, frozen snapshot tree, and evaluator output.
  • Each checkpoint was frozen as a Git archive before evaluation. The official evaluator used a clean Python 3.12 Docker environment.
  • After a provider/tool turn showed no progress for the fixed observation budget, the turn was cancelled once and preserved as incomplete evidence. It was not silently retried.

Benchmark references: SlopCodeBench runner and official problem catalog.

Correctness Boundary

The benchmark supports one narrow session contract:

provider or tool turn starts
  + no tool result or assistant completion
  + no delivered workspace change
  -> incomplete durable session
  -> never success, never successful idle

The token-limit case is one instance. A tool-call turn that never receives its result is another. The exact lower-level cause remains open where the run did not capture a provider or tool-server error; the state mapping is still wrong if it claims completion.

The correction should be narrow: preserve the durable session, provider termination reason, and incomplete outcome. Do not add automatic retry, alternate model selection, silent compaction, fabricated completion, or a fallback success path.

Boundary Findings

Clean delivery is separate from host execution

Self-tests on the host do not prove a delivered snapshot is runnable. The file-backup task passed only error-shaped checks before the clean evaluator exposed the missing dependency. A task-completion gate must execute the frozen artifact in a clean environment.

Prompt text is not filesystem isolation

The file-backup run created 126 files under host-global /tmp/bstest. The follow-up migration run also wrote a large test script under host /tmp. Separate Git/storage/TMPDIR roots prevented cross-problem contamination in the benchmark, but they did not constrain arbitrary process writes. Full isolation belongs in the launcher/process boundary.

Swarm topology was not the failure

Earlier real Swarm runs showed durable parent-child edges, dequeued messages, and conservative need_review states when workers produced no commit or when conflict resolution changed patch shape. No evidence justifies weakening those delivery gates or adding a compatibility fallback.

Next Work

  1. Instrument the turn boundary so provider finish reason, tool-call dispatch, tool result, process exit, and durable session projection are one inspectable timeline.
  2. Add a fail-first scenario for a tool call whose result never arrives; assert non-success and durable incomplete state.
  3. Keep clean-snapshot execution as a separate adopter gate and report dependency failures as delivery failures.
  4. Replace prompt-only filesystem restrictions with an OS-level launcher boundary before making confinement claims.
  5. Do not change Swarm delivery semantics until a benchmark shows a message or topology correctness failure.
