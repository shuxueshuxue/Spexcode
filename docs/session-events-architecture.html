从 Action 到 Event，再到可回放的 Session

这张图把 session-protocol、session-topology、session-events 和 session-application 放在同一个可检查的模型里。它描述下一版的目标形态，不把尚未实现的事件日志或 replay 说成当前功能。

当前：protocol + topology + self-launch下一版：events + applicationZSwarm / Spex adopter

1. 依赖方向

底层包只提供自己的事实和能力；跨模块的业务动作由 application layer 编排。箭头表示依赖，虚线表示 adopter 注入的实现。这里的 application 是向下编排者，不是 topology 的并列兄弟。

依赖的准确说法：session-application 语义上依赖 session-topology，因为它要在同一个 Unit of Work 中调用关系变更与 recipient 解析；它同时依赖 session-events 和 session-protocol。反向关系全部禁止：topology、events、protocol 不调用 application。
当前已落地/验证的基础下一版共享层adopter-owned 边界

2. 一次状态变化的事务

状态语义属于 adopter；事件、recipient 查询和消息入队由 application service 组合。SQLite transaction 是唯一提交边界。

不需要 outbox：状态事实、domain event 和 protocol message 在同一数据库内提交。只有跨数据库或外部 broker 时，transactional outbox 才重新成为独立组件。

3. Event、Message、Action 的区别

Action / Command

请求系统做某件事，例如“把 child 变成 review”。它可以被拒绝；尚未进入 handler 的输入不产生持久 event。

application.execute({
  actionId,
  name: "session.state.change",
  args: { sessionId, next: "review" },
})

Domain Event

已经发生的不可变事实。它是审计和 replay 的权威来源，不携带活对象，不依赖当前进程是否仍在运行。

eventStore.append(tx, {
  eventId,
  type: "session.state.changed",
  schemaVersion: 1,
  subjectSessionId: sessionId,
  payload: encode({ next: "review" }),
})

Protocol Message

发给特定 recipient 的投递物。它是 event 的 delivery projection，不应与 domain event 再形成第二个事实源。

tx.enqueue(recipientId, {
  kind: "event.reference",
  body: encode({ eventId }),
  idempotencyKey: `${eventId}:${recipientId}`,
})

Live Signal

wake hint、agent handle、进程状态和 observer 回调都是瞬时信号，不进入 domain event。丢掉它们不能改变 durable correctness。

wakeHint.notify(recipientId)
// optional latency optimization only
// next sweep can still call dequeue()
单一事实源：不要让 timeline、protocol_messages 和 session_events 同时记录同一个 domain fact。一个事实只能有一个 canonical feed。

4. Replay 需要什么

确定性回放不是“再调用一次 provider”。它是用固定事件、固定引用对象和固定代码版本，重新计算 session projection。

type ReplayInput = {
  events: readonly SessionEvent[]
  artifacts: ContentAddressedStore
  codeVersion: string
}

function replay(input: ReplayInput): SessionProjection {
  let state = emptyProjection()
  for (const event of input.events) {
    state = reduce(state, resolvePayload(event, input.artifacts))
  }
  return state
}
规则理由
未知 event 默认拒绝；显式 ignorable 才可跳过避免“能解析但静默漏掉状态”的假回放
writer bump schema version写入方知道旧 reader 是否还能保留语义
replay 不自动重做外部副作用重建状态和再次发送邮件、写 Git、调用 provider 是两种完全不同的行为
projection 可重建，event 不可修改修正用补偿 event，而不是改历史事实

5. 最终代码形态

下面是目标形态的最小 TypeScript 轮廓。它展示依赖方向和事务边界，不代表当前仓库已经提供这些新 API。

// @spexcode/session-events
export interface SessionEvent {
  eventId: string
  eventSeq: number
  type: string
  schemaVersion: number
  subjectSessionId: string
  payload: Uint8Array
  occurredAtMs: number
}

export interface EventStore {
  append(tx: ProtocolTransaction, event: NewSessionEvent): SessionEvent
  read(sessionId: string, afterSeq?: number): SessionEvent[]
  replay(sessionId: string, atSeq?: number): SessionProjection
}
// @spexcode/session-application
// session_runtime_bindings is adopter-owned; protocol does not read it
export function createSessionApplication(deps: {
  protocol: SessionProtocol
  topology: SessionTopology
  events: EventStore
  stateStore: StateStore       // adopter-owned semantics
  bindings: RuntimeBindings    // validate before dequeue, never part of protocol schema
}) {
  return {
    execute(action: SessionAction): ActionReceipt {
      return deps.protocol.withTransaction((tx) => {
        const change = deps.stateStore.apply(tx, action)
        const event = deps.events.append(tx, change.event)
        const recipients = deps.topology.recipients(change.subjectSessionId, tx)

        for (const recipient of recipients) {
          tx.enqueue(recipient, {
            kind: "session.event.reference",
            body: encode({ eventId: event.eventId }),
            idempotencyKey: `${event.eventId}:${recipient}`,
          })
        }
        return { actionId: action.actionId, eventId: event.eventId }
      })
    },
  }
}
// adopter code: event meaning stays outside the core packages
const app = createSessionApplication({ protocol, topology, events, stateStore })

app.execute({
  actionId: crypto.randomUUID(),
  name: "session.state.change",
  args: { sessionId: childId, next: "review" },
})

// a listener remains a consumer, not part of the transaction
const binding = bindings.resolve(parentId)
if (!binding || !adapter.isReady(binding)) throw new Error("runtime binding unavailable")
const message = protocol.dequeue(parentId)
if (message) handleEventReference(message)
Implementation order: first freeze session-events schema and replay contract; then implement the thin application service; finally prove the same child-state → event → watcher delivery flow in Spex and ZSwarm. Do not retrofit the current v1 protocol silently.
