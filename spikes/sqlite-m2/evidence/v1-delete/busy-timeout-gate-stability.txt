Stability of the busy_timeout ordering gate: before and after.

WHY THIS EXISTS
The decision "busy_timeout must be the connection's first statement" was previously gated only by
`repeated cold opens by eight processes never lose the first-open race`, which is a probabilistic
race. Two honest runs of the same code disagreed -- one reported the flip gated, another reported it
firing zero vectors -- because the vector caught the wrong-order stub only sometimes. An
intermittent catch is not a gate.

BASELINE (the old, racing vector)
  cmd: for i in $(seq 1 12); do
         M2_ENGINE=../stubs/busy-timeout-after-version-probe.mjs M2_COLD_OPEN_ROUNDS=6 M2_BENCH_MS=300 \
           node --test test/concurrency.test.mjs | grep -q '^✖ repeated cold opens'
       done
  result: the wrong-order stub was caught in 8 of 12 runs (missed 4).

THE REPLACEMENT (deterministic, not a race)
  vector : "busy_timeout must be the connection's first statement, or the version probe has no budget"
  file   : test/concurrency.test.mjs
  holder : a second OS process (worker.mjs op `lock-holder`) taking PRAGMA locking_mode=EXCLUSIVE,
           which retains the file lock after COMMIT. It releases itself after the window; it is not
           killed, so the release is real.
  window : 1500 ms hold, started only after the holder prints its own "held" line
  control: open with a 200 ms budget -> MUST fail PROTOCOL_DATABASE_BUSY. This proves the lock is
           genuinely held, so a later success cannot be a false pass.
  assert : open with an 8000 ms budget -> MUST succeed, and MUST have taken >= 40% of the hold,
           proving it waited rather than slipping past an unlocked database.

  Correct order sets busy_timeout before the first database-touching statement, so the version probe
  blocks and then succeeds. Wrong order runs that probe while busy_timeout is still its default 0,
  so it is refused immediately and open fails with PROTOCOL_DATABASE_BUSY.

STABILITY, 20 repeats each
  cmd: node --test --test-name-pattern 'busy_timeout must be' test/concurrency.test.mjs
  canonical engine ................................. pass 20/20, fail 0/20
  cmd: M2_ENGINE=../stubs/busy-timeout-after-version-probe.mjs (same command)
  wrong-order stub ................................. caught 20/20, missed 0/20

SUPPORTING MECHANISM (probe-lock-holder.mjs)
  setting busy_timeout while EXCLUSIVE is held : succeeds -- it needs no lock, which is what makes
                                                 the two orderings separable at all
  probe with busy_timeout=0                    : refused after 0 ms  (ERR_SQLITE_ERROR database is locked)
  probe with busy_timeout=300, hold outlasts it: refused after 313 ms
  probe with busy_timeout=5000, hold 700 ms    : succeeded after 717 ms, having waited
