Session 管理重构方案

把当前散落在 session.json、timeline、pending queue、cursor、watcher、lock 和 runtime receipt 中的状态，按责任迁入一个 adopter-owned SQLite 数据库与明确的 adapter 边界。

本页目录 现状与目标 物理部署 最小 Schema 核心事务 跨进程投递 Topology 与扩展 现有实现映射 迁移里程碑 验证矩阵 运维与备份 风险与守则

1. 从多文件状态机收缩到数据库事务

当前实现已经证明了消息、幂等、queue、timeline、topology notification 和 runtime delivery 的产品价值；问题在于这些价值由多个文件、多个锁与补偿逻辑共同维持。SQLite 迁移的目标不是改变用户行为，而是删除物理协调机制。

2. 物理部署与连接模型

一个 application state instance 使用一个 SQLite 数据库。每个 CLI、hook、backend 或 runtime 进程各自加载 SQLite library、打开同一路径；不存在中央 SQLite daemon。

CLI process ─────────┐
Hook wrapper ───────┼── SQLite connection ── application.db
Spex backend ───────┤                       application.db-wal
Z-Storm runtime ────┘                       application.db-shm

数据库路径

openSessionDatabase({ databasePath }) 只接收显式绝对路径。文件名与全局配置属于 adopter：

  • Standalone session manager 可以默认 <stateRoot>/sessions.db。
  • SpexCode 可以把 session 表扩展进自己的 <stateRoot>/spexcode.db。
  • Z-Storm 可以使用自己的 application database。

每个连接的强制设置

Connection bootstrap 
PRAGMA foreign_keys = ON;
PRAGMA journal_mode = WAL;       -- 必须验证返回值为 wal
PRAGMA synchronous = FULL;       -- 当前低写频率优先 durability
PRAGMA busy_timeout = 5000;

SELECT sqlite_version();         -- 拒绝已知不安全的 WAL 版本

WAL 仅允许同一主机上的进程共享。数据库路径若位于不可靠的 network filesystem，启动应 fail loud。不要把 -wal 和 -shm 当应用文件管理。

3. 最小数据库 Schema

目标 schema 刻意很小：一张 migration registry、一张 session address 表、一张包含 FIFO 与交付状态的 message 表。SQLite transaction 已经是 journal，因此不再创建应用 outbox 或 event log。

3.1 Component migration registry

Schema 
CREATE TABLE schema_migrations (
  component     TEXT    NOT NULL,
  version       INTEGER NOT NULL,
  checksum      TEXT    NOT NULL,
  applied_at_ms INTEGER NOT NULL,
  PRIMARY KEY (component, version)
) STRICT;

每个 package 拥有自己的 component name 与顺序 migration。Checksum 防止已经应用的 migration 被静默改写。不能使用单个 PRAGMA user_version 让所有 adopter 争抢一个整数。

3.2 Protocol sessions

Schema 
CREATE TABLE protocol_sessions (
  session_id    TEXT    PRIMARY KEY,
  created_at_ms INTEGER NOT NULL,
  retired_at_ms INTEGER,
  CHECK (length(session_id) BETWEEN 1 AND 255),
  CHECK (retired_at_ms IS NULL OR retired_at_ms >= created_at_ms)
) STRICT;

这张表取代 universal session.json。它只表达 protocol participation，不表达 governed、parent、worktree、harness 或 lifecycle。Retired row 是 tombstone，可区分已退役地址与拼错 ID。

3.3 Messages and FIFO state

Schema 
CREATE TABLE protocol_messages (
  enqueue_seq      INTEGER PRIMARY KEY AUTOINCREMENT,
  message_id       TEXT    NOT NULL UNIQUE,
  target_session_id TEXT   NOT NULL
    REFERENCES protocol_sessions(session_id),
  sender_session_id TEXT,
  kind             TEXT    NOT NULL,
  body             BLOB    NOT NULL,
  headers_json     TEXT    NOT NULL DEFAULT '{}'
    CHECK (json_valid(headers_json) AND json_type(headers_json) = 'object'),
  idempotency_key  TEXT,
  payload_hash     BLOB    NOT NULL CHECK (length(payload_hash) = 32),
  enqueued_at_ms   INTEGER NOT NULL,
  dequeued_at_ms   INTEGER,
  UNIQUE (target_session_id, idempotency_key)
) STRICT;

CREATE INDEX protocol_pending_fifo
  ON protocol_messages(target_session_id, enqueue_seq)
  WHERE dequeued_at_ms IS NULL;

body 与 headers 是 opaque bytes/data；protocol 只比较和存储。enqueue_seq 是稳定 FIFO/cursor。Message payload 不可修改，只有 dequeued_at_ms 发生一次 NULL → timestamp 状态转换。

为什么没有 queue table：partial index 已经把 dequeued_at_ms IS NULL 的消息变成高效 FIFO work list。单独 queue projection 会重新引入同步状态。

4. 核心 ACID Transactions

所有写操作使用同步短事务。Transaction 中只执行 SQL 与纯内存校验；严禁等待 harness、网络、终端、文件复制、Git 或异步 callback。

4.1 Initialize

BEGIN IMMEDIATE取得 writer reservation
Read session不存在则插入；active exact replay 幂等
Validateretired 或 identity conflict fail loud
COMMIT地址对所有进程可见

4.2 Enqueue

BEGIN IMMEDIATE写事务开始
Validate target必须 initialized 且未 retired
Check keyexact replay 返回原结果；changed bytes conflict
INSERT message消息与 pending 状态是同一 row
COMMITDurable queue transition

没有“先写 timeline，再写 pending”的 crash window，也没有 reconcile。Unique constraint 与 payload hash 共同实现 idempotency。

4.3 Dequeue

Transaction 
BEGIN IMMEDIATE;

SELECT *
FROM protocol_messages
WHERE target_session_id = ?
  AND dequeued_at_ms IS NULL
ORDER BY enqueue_seq
LIMIT 1;

UPDATE protocol_messages
SET dequeued_at_ms = ?
WHERE enqueue_seq = ?
  AND dequeued_at_ms IS NULL;

COMMIT;

SQLite 的 single writer 保证两个 consumer 不会成功 dequeue 同一个 head。Crash 在 commit 前，消息仍 pending；crash 在 commit 后，消息已交付，不自动回队。

4.4 Retire

协议的 retire 要求 queue 已空，然后原子写入 retired_at_ms。如何处理尚未消费的消息属于 adopter policy：adopter 可以在 transaction 外决定拒绝关闭，或明确 dequeue 并丢弃；protocol 不增加隐式 cancellation 模式。

4.5 Topology mutation + notification

One database transaction 
BEGIN IMMEDIATE;

UPDATE topology_edges ...;          -- reparent / subscribe / detach
INSERT INTO protocol_messages ...;  -- zero or more deterministic notifications

COMMIT;

这是“不需要 outbox”的原因：关系事实与要发送的消息同属一个 SQLite transaction。若未来跨数据库或发往外部 broker，才引入标准 transactional outbox。

5. 从状态写入到 input box 的跨进程链路

ProducerCLI/hook/backend import package
SQLite commit消息已经 durable pending
Wake hint可选 IPC/in-process signal
Runtime dequeue数据库是唯一事实
Adapter input写 native thread/TUI/input seam

Correctness 与 latency 分开

  • Correctness：commit 后 pending row 存在；runtime 重启或数小时后查询仍能看到。
  • Latency：producer 可在 commit 后发 wake hint；hint 丢失、重复或延迟都不改变状态。
  • Fallback：resident runtime 做 bounded sweep。可用 PRAGMA data_version 减少无变化时的完整查询，但 polling 仍是 adopter policy。
  • 无 runtime：self-launch 消息保持 pending，直到显式 listener/monitor command dequeue。
不再依赖 file observer：fs.watch 不保证逐写事件，可能 coalesce、丢失或延迟。它可以被某个 adopter 用作 hint，但不进入 protocol package，也不拥有 correctness。

CLI 还是 import？

Node producer 直接 import package。Shell hook 或非 Node 环境调用薄 CLI；CLI 只解析参数并调用同一 library，不是后台进程。Resident backend 只在需要自动将 pending 交给 harness 时存在。

6. Adopter 如何扩充同一个数据库

扩展不是向 session.json.metadata 塞任意字段，也不是修改 protocol table。每个 component 通过自己的 migrations 创建拥有明确责任的表，并登记在 schema_migrations。

Illustrative topology extension 
CREATE TABLE topology_edges (
  edge_id         TEXT    PRIMARY KEY,
  from_session_id TEXT    NOT NULL REFERENCES protocol_sessions(session_id),
  to_session_id   TEXT    NOT NULL REFERENCES protocol_sessions(session_id),
  relation_type   TEXT    NOT NULL,
  revision        TEXT    NOT NULL UNIQUE,
  created_at_ms   INTEGER NOT NULL,
  removed_at_ms   INTEGER,
  CHECK (from_session_id <> to_session_id)
) STRICT;

CREATE UNIQUE INDEX topology_active_edge
  ON topology_edges(from_session_id, to_session_id, relation_type)
  WHERE removed_at_ms IS NULL;
Illustrative Spex adopter extension 
CREATE TABLE spex_governed_sessions (
  session_id       TEXT PRIMARY KEY REFERENCES protocol_sessions(session_id),
  project_id       TEXT NOT NULL,
  lifecycle        TEXT NOT NULL,
  proposal         TEXT,
  worktree_path    TEXT NOT NULL,
  branch_name      TEXT,
  harness_id       TEXT NOT NULL,
  native_session_id TEXT,
  revision         INTEGER NOT NULL DEFAULT 0
) STRICT;

扩展规则

  1. 表名与 migration component 必须有明确 owner。
  2. Adopter 只能通过 protocol public API 或同 transaction 的受控 internal capability 写 protocol tables。
  3. 禁止 EAV/generic metadata table 代替正常 schema。
  4. 跨 component 原子行为必须发生在同一个同步 transaction 中。
  5. Topology 先保持 internal；两个真实 adopter 证明语义相同后再发布 package。

8. 分阶段迁移，不做 big bang

M0

冻结协议语言

确认 initialize/enqueue/dequeue/read/retire、at-most-once 边界、error codes 和 database scope；建立 SQL schema 与语言无关 conformance fixtures。

M1

先收缩 API，不换 storage

在当前 package 上引入纯 dequeue，移除 adapter callback；runtime 自己循环。这样 storage migration 不与语义 migration 混在一起。

M2

SQLite implementation 与 conformance

实现 TypeScript store、migrations、version gate、schema constraints 和多进程测试。此阶段不接产品，只与 file implementation 跑相同 test vectors。

M3

兼容 release

所有新版本 CLI/hook/backend 先学会识别 storage generation 与拒绝跨 generation 写入，为离线 cutover 建立统一门禁。禁止长期 dual-write。

M4

一次性离线导入

停止目标 state root 的 writer，备份旧 store，验证每个 identity/queue/timeline/topology record，在一个 migration transaction 中导入；比较数量、顺序、hash 与 tombstone，再切换 generation。

M5

三 adopter YATU

Self-launch offline enqueue/listen、Spex governed dashboard/hook/backend、Z-Storm runtime loop 全部通过，且 lost wake/restart 仅靠数据库恢复。

M6

退役 legacy

旧文件改为只读 compatibility evidence，经过一个明确 release window 后删除 writer、lock、reconcile 和 internal exports；再评估独立 repository。

为什么不 dual-write：两个 writer path 会产生两个 authority，最危险的失败恰好是“一边成功、一边失败”。迁移应是可回滚的离线 cutover，不是无限期镜像。

性能门槛

基准使用真实预期负载与更高压力：平均 50 次短写/秒、100B payload；再测 10× burst。目标不是追求极限 QPS，而是证明 lock hold time 只包含 SQL，p99 latency 有界，WAL 不持续增长。

10. 管理、可视化与备份

  • 权威检查：sqlite3 CLI、.schema、.indexes、.eqp、PRAGMA integrity_check、PRAGMA foreign_key_check。
  • 人工浏览：DB Browser for SQLite 或 Letos；连接 live WAL database 时优先只读模式。
  • Browser inspection：sqlite-web --read-only 仅绑定 localhost，不进入产品 runtime。
  • Schema review：plain SQL 进入 Git；可用 sqldef/sqlfu 生成 draft，但 migration 必须人工审阅。
  • 备份：使用 SQLite backup API 或 VACUUM INTO。Live WAL 模式下不能只复制主 DB 文件。
  • 持续异机备份：只有产品需要时再采用 Litestream；它是独立运维进程，不属于 protocol。

最终复杂度判断：SQLite 的引入只在它删除更多机制时成立。目标实现应比当前文件协议少：一个 transaction engine、一个 schema authority、一个 queue state、一个关系 authority。若重构后仍保留旧 locks、journal、pending projection、outbox 和 observer correctness，说明迁移失败。
