一支 6 条 lane 的队伍在 2026-08-06 一天之内**四次**撞到同一个形状,每次换个位置长出来:

1. contracts dist gate 在 `17:23:12` 就已满足(Build Records 有 `dist/index.js` mtime 证据),但下游 lane 一直
   在等它;而上游 parked 的 note 写「等待新的队列事件」—— 双方都在等对方,谁都没错。
2. 队列顺序已定,没送达。
3. 席位授予已发生,没送达。
4. 一条 lane 的 GO 已被批准,它仍挂在 `asking` 等。

同一天另有一条更硬的证据:一位指挥官宣布「已同令参谋长广播 C6-d」,交叉核对它全部 **250 次 `spex session *`
调用**后确认**那次 send 根本不存在**,该闸只到达了发明它的那条 lane。补投后回执原文:「**这是我第一次收到**
C6-d、位子单位、fail-reading 单向门与 v2.3 全文」——**其中 `v2.3` 是定义「什么才算交付」的总闸,此前从未到达
三条 lane,它们一直在用更松的标准判断自己是否完成。** 同族「说已发但查无 send」在该指挥官身上共 7 次,自认 1 次。

## 缺口在哪

`spex session send` 的成功判据是**时间线 append 成功**,即「我发出去了」。产品里没有任何东西回答另外两问:

- **送达面**:这条授予/解除**落到对方身上了吗**?(不是 append 成功,是对方的上下文里真的有了)
- **反查面**:一条 lane 无法反问「**我现在受哪些闸约束**」。它只能相信自己收到过的那些。

于是形成一个**结构性盲区**:守纪律的下游**不轮询**(轮询本身是被明令禁止的浪费),所以缺一条闸时,
它看到的世界与收到了那条闸时**完全一样** —— 没有任何可观测差异让它发现自己少了什么。
盲区越是被纪律良好的队伍触发,越难发现:纪律越好,越不会去戳。

指挥官已在纪律层打了补丁(「广播须附逐条目标 id + sent 结果,不以宣称替代投递」),7/7 sent 也确实立刻
挖出了三条 lane 从未收到 v2.3。**但这说明补丁有效,不说明缺口不存在** —— 靠每个指挥官自觉不宣称,
是把一个机制责任摊给纪律。

## 值得考虑的方向(不是设计,是入口)

- 一次广播应当有**可复读的投递账**:发了什么、发给谁、每个目标的结果,supervisor 事后能重读而不是回忆。
- lane 侧需要一个**「我当前受哪些约束」的可查面**,让缺失可被下游自己发现,而不是只能由上游发现。
- `session watch` 已经解决了同构的另一半(状态变更的送达),这条缺口是它在**授予/解除**方向上的对偶。

开这条 issue 之后,同一支队伍在同一天里又撞到两次,而且**这个现象比我最初写的更窄也更恶劣**。补三格:

## ① 它专挑守纪律的人下手 —— 所以不能靠「让下游多问一句」修

五次实例现已并列(全部同一天、同一支队伍、五个不同位置):
```
1  contracts dist gate 17:23:12 已满足    -> 下游一直在等
2  队列顺序已定                            -> 未送达
3  席位授予已发生                          -> 未送达
4  GO 已批准                               -> 下游读到的是旧 note 快照
5  预期为空未声明                          -> 下游把正常当故障去 debug
```
前四例的下游**都严格不轮询**(轮询在这支队伍里是被明令禁止的浪费)。
**⇒ 正因为守纪律,它们对「未送达的授予」永久不可见。** 一个纪律越好的团队,这个洞越深。
这也是为什么「让 lane 定期问一下」不是修法 —— 那等于要求下游用违反纪律来补偿机制缺口。

## ② `sent` 不证明送达,更不证明未损坏 —— 第二层缺口有实证

指挥官给一条 lane 发更正判据时 **shell 引号用错、反引号被解释执行**,终端报了六行 `command not found`;
**`session send` 照常返回 `sent`。** 内容是否完整送达只能靠人回读发现。
```
send 目前只回答:我把它 append 进时间线了吗
它不回答:  对方的上下文里真的有了吗
也不回答:  送过去的东西还是我写的那个东西吗
```
纪律层的补丁(「广播须附逐条目标 id + sent 结果」)确实立刻挖出了三条 lane 从未收到过 `v2.3`
——**那条闸定义「什么才算交付」,三条 lane 一直在用更松的标准判断自己完成没有。**
但补丁有效不等于缺口不存在:它把机制责任摊给了每个指挥官的自觉。

## ③ 反查面才是真修法的位置

最值钱的一格是:**那三条 lane 没有任何办法主动查出自己缺了 v2.3。**
它们是在补投时才知道的 —— 也就是说,**发现缺口的唯一途径是上游恰好又发了一次**。
⇒ 产品侧需要的不是更强的 send 回执,而是一个**「我现在受哪些约束」的可查面**:
让缺失能被下游自己发现,而不是只能由上游发现。
`session watch` 已经解决了同构的另一半(状态变更的送达),这条缺口是它在**授予/解除**方向上的对偶。

## 给未来读者的启发式
