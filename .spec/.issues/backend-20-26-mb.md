Spec: spec-cli, host-resource-budget

## 现象

一个 `spex serve` supervisor 的后端子进程（`spec-cli/src/index.ts`）常驻内存随存活时间单调增长，
速率约 **20–26 MB/分钟**，未观察到平台期。

两次独立观测，速率一致：

| 实例 | 存活 | RSS | 折合 |
|---|---|---|---|
| 第一个（被替换前） | 141 min | 2792 MB | ≈ 20 MB/min |
| 第二个（重启后新起） | 84 min | 2158 MB | ≈ 26 MB/min |

第二个实例是把第一个实例的父进程 TERM 掉、由 supervisor 按设计自动重拉的全新子进程，
从零开始重新走同一条曲线。**重启使 RSS 归零，但不改变增长速率。**

该实例的负载不是用户流量高峰：观测期间它的累计 CPU 是 421 s / 84 min（约 8%），
公开端口（该部署的对外网关）在整个观测窗口只返回稳定的 302，无异常请求量。

## 影响

- 单进程按此速率 24 小时约需 30 GB，会独力耗尽一台 32 GB 宿主。
- 它至今没有造成故障，**只是因为源码变更会频繁触发 supervisor 的热重载**，等于隐式地定期重启它。
  也就是说：一个开发期高频发生的行为，一直在掩盖一个生产期会致命的泄漏。部署环境越稳定
  （源码越少变动），这个泄漏越容易发作。
- 它同时使 `host-resource-budget` 的 `backendRssMiB` 预算（默认 2048 MiB）在约 80–100 分钟后
  必然被突破，于是该预算报出的 `rss-over-budget` 在这类宿主上长期为真，降低了该字段的信噪比。

## 复现

1. 启动一个 `spex serve`（本次观测的是被部署网关派生的那一个，`--port <n>`）；
2. 记录 supervisor 的孙进程（真正的 `index.ts` 后端）PID；
3. 每 30 分钟采一次 `ps -o rss= -p <pid>`，同时记录 `/proc/<pid>/stat` 的 utime+stime；
4. RSS 单调上升且不随请求量回落即复现。

停止对照：把该后端的父进程 TERM 掉，supervisor 会零停机重拉一个新子进程，公开端口不中断
（本次实测对外 HTTPS 前后均为 302）；新子进程从低位重新开始同一条曲线。

## 尚未定位

本报告只确立「存在、可复现、速率稳定、与请求量不相关」，未定位到具体的持有者。
下一步应在一个受控实例上取堆快照（相隔 30 分钟两次，比较 retained size），
而不是继续从外部观察 RSS。

撤回本 issue 的核心断言：**后端不是内存泄露**。原判据是拿单点 RSS ÷ 运行时长推出「20-26 MB/分钟单调增长」，这个方法本身不成立——它假设进程从 0 线性增长。用两台机器的多点采样重测，结论相反。

**macmini / gugu（darwin，dist 构建路径）** —— 先杀掉跑了 94 分钟、RSS 1758 MB 的 child，supervisor 重生新 child，然后跟踪它：

```
age=00:05  rss= 241MB
age=01:47  rss=2043MB    ← 峰值，比被杀那个跑 94 分钟的还高
age=02:32  rss=1513MB
age=02:52  rss=1512MB
age=03:12  rss=1513MB    ← 平
```

启动 2 分钟内撑到 ~2 GB 峰值，回落到 ~1.5 GB 后不动。旧 child 跑 94 分钟是 1758 MB，新 child 3 分钟就 1513 MB —— 90 分钟只差 245 MB，且非单调。

**thinkpad（linux，tsx dev 路径）** —— 主后端 child pid=789298，已运行 11418s（3.17 小时），90 秒内四点采样：

```
1741MB / 1741MB / 1742MB / 1739MB
```

平的，±3 MB 抖动。而同一轮 `spex session resources` 的 tick diff 显示它 1980 → 1905（**-76**），方向朝下。此前我据以立案的那些 +76 之类的 tick 增量，是平台期附近的噪声，不是单调增长。

**因此重启不是「止痛」，是无效**：macmini 那次重启把 1758 MB 降到 241 MB，90 秒后就回到 2043 MB，比重启前更高。任何把「后端超预算」翻译成「重启回收」的运维动作都应当撤销。

**真正剩下的事实（值得单独立案，不在本 issue 范围）**：后端稳定态工作集在两台机器上都是 1.5–1.7 GB，且在启动 2 分钟内就达到。对一个后端来说这个基线很大，值得查它开机加载了什么（session ledger / spec graph 的全量驻留是首要嫌疑）。但那是容量问题，不是泄露问题，处理方式完全不同。

**方法学教训**：单点 RSS÷age 不能推增长速率；要立「泄露」必须给同一 PID 的多点时间序列。本 issue 的原始证据不满足这个门槛。
