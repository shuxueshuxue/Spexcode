Construction control · review draft

Session Platform 施工路线、Session 分配与检阅图

把总体设计变成可合并、可反证、可拆除、可回滚的施工序列。这里管理的不是任务数量，而是每个 semantic milestone 的唯一 writer、独立 reviewer、真实 adopter proof 和 legacy deletion gate。

硬规则：任何 adopter milestone 都必须同时完成新路径接入、旧设施对抗式失效和物理删除。只增加新实现、不减少旧设施，不算重构完成。
本页目录 施工单元 依赖图 Session 分配 里程碑 Legacy 删除表 对抗式攻击 检阅图 证据与门禁 迁移与回滚 开工清单

1. 施工单元不是 feature，而是 cutover

Foundation milestone 可以建立独立能力；adopter milestone 不允许只把新能力接到旧系统旁边。它的最小闭环固定为四步：

1. Adopt通过公开 surface 使用新 protocol、topology 与 runtime adapter，完成真实端到端行为。
2. Inventory列出被替代的 reader、writer、锁、observer、文件、配置、CLI 与 spec ownership。
3. Sabotage让旧目录缺失、旧文件损坏、旧 observer 停止，证明新路径仍然完整且没有访问旧设施。
4. Delete物理删除旧实现和生成物；静态边界、文件访问轨迹和 YATU 一起证明不可达。
零兼容容忍：normal runtime 禁止 dual-read、dual-write、fallback、永久 translation adapter、旧环境变量 alias 和“临时” compatibility re-export。若必须保留用户数据，只能通过显式、一次性、单向 migration 转换；转换完成后 runtime 不再识别旧格式。

每个 milestone 的净结果必须是机制更少，而不只是代码更多。删除数量不以 LOC 为目标，而以权威数据源、写入路径、锁、观察器、进程角色和配置入口的数量为目标。

3. Session 分配与所有权

最多同时运行四个 session：一个 integration coordinator 加三个互不重叠的 worker/reviewer。Session 在依赖满足时才创建，不提前维持空闲 writer。名称是角色，不是永久团队。

4. 里程碑与 merge exit

M0

Clean baseline 与设施台账

合并已验收设计，关闭仅属于本 campaign 且已落地的旧 worktree，运行全局 build/spec/eval，记录当前所有 session persistence reader、writer、lock、observer、process 和 config entry。

Exit：唯一 integration head；每个 legacy element 有 owner、last consumer、deletion milestone。
Rollback：无生产变化。
M1

固定 protocol contract

冻结 initialize/enqueue/dequeue/listPending/readMessages/retire、错误类型、transaction semantics、schema migrations 和 language-neutral conformance vectors。

Exit：fresh-context agent 可只读 spec 实现同样行为；API 中没有 topology、harness 或 product 名称。
删除：未落地的旧术语、callback drain contract 和第二套 schema 描述。
M2

SQLite engine 与反证实验

实现显式 databasePath、短同步 transaction、migration registry、FIFO/idempotency；用多进程、SIGKILL、busy、checkpoint、backup 与 corrupt fixture 攻击。

Exit：500 short writes / 10s 与更高 burst 无丢失或重复 dequeue；transaction 内没有外部等待。
禁止：产品接线、ORM、daemon、outbox、file observer。
M3

Internal topology foundation

建立 neutral edge schema 与同 transaction topology mutation + enqueue capability。只证明关系模型，不发布 package。

Exit：Spex 与 ZSwarm 的关系 fixture 都可表达，core 不出现 adopter role。
删除：重复 parent/watcher 概念只能在 M6 最终 cutover 后物理移除。
M4

Self-launch adopter cutover

没有 backend 时 initialize/enqueue；稍后显式 listen/dequeue。将旧 listener/queue 路径置为缺失和损坏再跑同一 YATU。

Exit：公开 self-launch loop PASS；file observer 完全停止仍正确。
删除：self-launch 对旧 queue、固定 Spex root 和 governed record 的所有依赖。
M5

ZSwarm adopter cutover

使用自己的 DB path、topology 与 runtime loop；在仓库外 clean consumer 中安装 protocol package，不提供任何 Spex runtime。

Exit：ZSwarm workflow PASS；依赖图中没有 Spex package。
删除：ZSwarm 侧旧消息持久化、关系投影和兼容 adapter。
M6

Spex governed adopter cutover

CLI、hook、dashboard producer 直接使用同一 package；backend 只负责 wake/drain，restart reconciliation 查询数据库。Lifecycle 与 native runtime proof 留在 adopter-owned tables/adapters。

Exit：真实 governed parent/child、离线 pending、restart/lost-wake YATU PASS。
删除：pending/timeline/cursor JSON authority、delivery/record locks、watchers/parent 双 authority、runtime-session bridge 和 observer correctness。
M7

一次性 legacy data migration

停止旧 writer，备份旧 store，显式运行 importer，在一个受控 cutover 中验证 identity、FIFO、history、topology、tombstone 的 count/order/hash，再把旧 root 移出 runtime path。

Exit：新 runtime 在旧 root 不可读时完整启动；normal package dependency graph 不包含 importer。
Rollback：只允许恢复 pre-cutover backup 与旧 release，不允许 live fallback。
M8

Final demolition

删除所有旧 reader/writer、compatibility package/re-export、lock/reconcile、old generation config 和过渡 specs。运行 static reference、generated file 与 file-access trace 三重审计。

Exit：legacy references=0，legacy generated files=0，runtime legacy reads=0，设施台账净减少。
停止条件：任何 last consumer 尚未 cutover。
M9

Package release 与 repository decision

clean install 三 adopter，发布完整名称的 package。只有公开 API、migration ownership 和两个非 Spex adopter 已稳定时才决定是否拆独立 repository。

Exit：registry consumer 无 monorepo/source fallback；post-release YATU 与 backup restore PASS。

明确保留，不属于 legacy

  • Artifacts、files/web evidence 和大文件引用。
  • Harness 必须发现的 materialized hooks、contracts、skills 和 commands。
  • Native launch proof、PID、socket、endpoint 与 unload proof；它们由 harness runtime adapter 拥有。
  • Spex lifecycle、worktree、branch、proposal 等产品事实；它们迁到 adopter-owned schema，而不是进入 protocol。

7. 独立检阅图

同一个 session 不得同时扮演 author、adversarial reviewer 和 evaluator。每个节点只接受前一个节点的固定 commit；任何修复都返回 writer，产生新 commit 后重新走完整后半段。

Writerspec first、fail-first、semantic commits、clean branch、proposal merge
Boundary reviewer新上下文检查责任、依赖方向、API 泄漏和 kill list
Adversarial reviewer同步 exact commit，执行 crash、sabotage、no-legacy trace
YATU evaluator真实 adopter surface，提交 fresh reading 与窄证据
Integratorancestor、diff、gates、atomic landing、post-merge CI

8. 每个 merge 必须携带的证据

  • Owning spec 已更新，且本次 proof 针对最终 spec wording。
  • Writer branch 已同步 exact integration head，ancestor gate 与 diff check 通过。
  • Positive conformance/YATU 通过；不是内部 helper 替代真实 surface。
  • Legacy kill list 有精确 owner、last consumer 与删除 diff。
  • Sabotage run 在旧设施缺失、损坏或不可写时通过。
  • Static import/export/reference audit 为零；runtime file-access trace 无旧路径。
  • Crash、restart、lost-wake、busy 和 backup/restore 中与本 milestone 相关的矩阵通过。
  • 新设施数量与删除设施数量已记录；本 milestone 没有增加第二 source of truth。
  • Evaluator reading 的 codeSha 指向已验证 product commit，evidence 窄而可人工检查。
  • Integrator landing 后重新运行 CI，并记录 rollback commit/data checkpoint。
合并公式：positive adopter PASS + legacy sabotage PASS + physical deletion PASS + independent review PASS + synced YATU PASS。缺任何一项，状态只能是 working/parked/asking，不能 proposal merge。

9. 数据迁移与回滚，不建立兼容运行时

  1. 停止目标 state root 的所有旧 writer，并验证 process census。
  2. 用 SQLite backup API、旧 store archive 和 manifest 建立同一 checkpoint。
  3. 显式执行独立 migration command；normal runtime package 不 import 它。
  4. 在单一 migration transaction 中写入新 schema；验证 identity、FIFO、history、topology、tombstone。
  5. 把 legacy root 改名为 quarantine，使新 runtime 无法通过旧 canonical path 读取。
  6. 只启动新 release，执行三 adopter smoke 与 legacy file-access trace。
  7. 失败时停止新 writer，恢复 checkpoint 和旧 release；禁止运行时自动 fallback。
  8. 超过明确 rollback window 后删除 quarantine；删除动作单独记录。

这条路径承担用户数据责任，但不会把兼容性带进日常代码。Importer 只存在于 migration milestone 和对应 release tooling；它没有长期 public runtime API。

10. 真正开工前的清单

  • 三份设计已合并到唯一 integration head，并打 session-platform-pre-refactor checkpoint。
  • M0 legacy ledger 已包含所有真实 reader、writer、lock、observer、process 与 config source。
  • 每个 element 都有 last consumer 和 deletion milestone；没有“以后再看”。
  • M1 conformance vectors 可以在没有 SpexCode context 时独立理解和运行。
  • M2 spike 已用真实多进程 SQLite 证明并发、crash 和 restart，而不是只靠设计推理。
  • 三个 adopter 的正向 YATU 与负向 sabotage fixture 已在实现前写清 expected。
  • 每个 writer/reviewer 的 scope 无文件重叠；最多四个 active session。
  • 最终 demolition reviewer 与 evaluator 尚未参与实现，保持 fresh context。
Go / no-go：只有 M0 ledger、M1 executable contract、M2 adversarial spike 和三个 adopter 的 cutover+deletion expected 同时存在，才开始 production integration。否则继续补证明，不用更多代码掩盖未知。
